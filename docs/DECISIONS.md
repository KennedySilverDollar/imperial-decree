**調査日**：2026-10-24

### 4.1 Structured Outputs の `minimum` / `maximum`
- **未確認**。検索では対応キーワード一覧を見つけられなかった。
- 分かったこと（第三者情報）：`response_format: { type: "json_schema", json_schema: { name, schema, strict } }` 形式。`strict` は既定 false（Vercel AI SDK の Mistral プロバイダ文書より）。
- **実装上の方針（確認結果に関係なく）**：スキーマで範囲を強制できなくても困らないよう、`magnitude ∈ [-100,100]`、`confidence ∈ [0,1]`、`budget >= 0` を**プロキシとフロントの Effect Schema で検証し、範囲外は clamp**（clamp したことは3段表示に出す）。`minimum`/`maximum` が非対応でエラーになる場合に備え、プロキシの固定スキーマは「範囲キーワードあり／なし」を定数で切り替えられるようにする。
- **P3 でやること**：公式ドキュメント（Custom Structured Outputs のページと API リファレンスの `response_format`）を確認するか、実 API に `minimum`/`maximum` 付きスキーマを投げて挙動を確かめる。

### 4.2 `mistral-small-latest` の価格
- **未確認**（公式価格ページに到達できず）。
- 第三者の価格まとめでの記載（2026年10月時点、いずれも米ドル／100万トークン）：
  - 入力 $0.15 / 出力 $0.60（Mistral Small 4 として。複数サイトが一致。キャッシュ入力 $0.015 の記載もあり）
  - 入力 $0.10 / 出力 $0.30（別のまとめサイト。古い可能性）
- SPEC §11.2 の「入力0.60 per M tokens」は、上記の**出力単価**と一致しており、入力・出力の取り違えの可能性がある。
- 規模感：勅令1回 ≈ 入力500＋出力100トークンと仮定すると、$0.15/$0.60 で1回約 $0.000135。50ターン×100プレイでも $1 未満。P0 のコストリスクは小さい。
- `mistral-small-latest` は**エイリアスで中身が更新される**ため、再現性を重視するならプロキシで日付付きモデル ID に固定することを P3 で検討する。

読み取り：
- **全域 2048² は予算 3.0 秒に収まらない。** 侵食を全くしなくても 2.6 秒（標高のノイズだけで約 1.9 秒）。粒子を半分にしても 3.8〜4.8 秒。
- **「全域 1024²＋村域だけ 2048²」（SPEC_v3.4 §3.4 の二段階解像度）なら、Node 1.6 秒・Worker 約 1.8 秒**（侵食 12万粒子）。予算まで約 1.2〜1.4 秒の余裕が残る。
- **代替案の比較**（収まらないときの手段）：①解像度を下げる（2048²→1024²）は 5.5→1.1 秒で最も効く。②粒子数を減らすのは侵食段階にしか効かず、2048² では標高（約 2 秒）が下限。③「侵食を村域外のみ」にしても村域は地図の約 3% なので時間はほぼ変わらない（品質面の意味はある。S-3 参照）。
- Node と Chromium の Worker で**ハッシュが一致**した（全6構成。同じ構成を3回実行しても同じ）。ただし両方とも V8 なので、BB-15（他エンジンでの一致）の確認にはならない。
- **未計測（このスクラッチに含めていない）**：等高線（marching squares）・ケバ・植生記号の配置・注記の配置・区画の Voronoi 緩和（d3-delaunay）・道路の A*・蛇行の付与・`ImageBitmap` 化とタイルのベイク・地名生成。これらは別途加算されるため、**1024²＋村域2048² の構成でも余裕は 1.2〜1.4 秒より小さくなる**。M1 の完了条件で計測し直す（下記）。
- 所要時間は開発コンテナの CPU（4コア）での値。実機（Ryzen AI 内蔵相当）の CPU 性能が下回る場合の安全率を見ておく（推奨：計測値が予算の 60% 以内）。

### 17.6 検証スパイク S-3：村域100区画の建設可能性（2026-10-27）

**方法**：同じスクラッチ。山並み・谷・段丘面・土手を解析的に彫り、侵食をかけ、水文で川網を引いて、村域の 10×10 区画（各60m四方の正方形。**多角形への吸着は含めない**）を検証した。10×10 の100区画すべて（十字の道路区画19＋役所1＋建物80を区別せず全区画）について、「水域でない」かつ「傾斜が5°以下」。シードは `save-1`〜（1000個）。不合格なら `attempt` を増やして再生成（上限8回）。区画の傾斜は標高を約15mに平滑化して計算。

**設計上の主な発見**（スクラッチを直した順）：
1. **川の蛇行を村の前後で抑えないと、本流が村域に入る**（初期実装は12シード中6個で本流が村域を貫通）。村の前後約500m〜1.2kmで蛇行をゼロに近づけて直線化し、村域を川から 600〜740m 離す必要がある。
2. **広域の起伏が谷の勾配に対して大きいと、窪地が大きな湖になり、水が地図中央に集まる**。川の縦断勾配を 0.6%→2.5%、広域ノイズを 18m→7m にして解消。
3. **段丘面は村域より広く平らに取る必要がある**（BB-23）。村域ちょうどで斜面に入ると、区画の傾斜計算が縁の斜面にかかり、全シード不合格になった（平均傾斜の最大が 6.5°）。村域の外へ60m延ばした。
4. **川のしきい値 0.25km² は不可能**（BB-14）。村域の段丘面自体の集水域が約0.4〜0.5km²あり、面を流れる水が全部「川」になる。1km² 以上なら成立する。
5. 土手（背面と上流側のL字、高さ2.6m）は効果が小さい（初回合格 +2.4pt）。丘の水を村域の外へ回す手段としては、再試行のほうが効いている。

### 17.8 承認結果（2026-10-27）
