## 1. 概要

| 項目 | 内容 |
|------|------|
| ジャンル | 都市開発シミュレーション × 官僚マネジメント × AI解釈ゲーム |
| コンセプト | 「AIに任せる」のではなく「AIを御す」都市開発 |
| UIコンセプト | 「机の上の書類と、広げた地図」（Paper, Please × Civilization） |
| 成長軸 | 村 → 町 → 都市 → 国家 |
| 時間軸 | 1ターン＝1年 |
| プラットフォーム | 製品版：Steam（PC）／プロト：ブラウザ |
| 価格 | 製品版 19.99（通貨は未記載・要確認） |
| 販売形態 | 体験版（無料）＋製品版。早期アクセスは不使用 |
| ターゲット | 都市開発/経営シム好き、プロンプトエンジニアリングに関心のある層、システム語りゲーム愛好者 |

### 1.1 本作の核心

プレイヤーは都市を直接操作できない。**勅令（自然言語）→ 側近の解釈 → 官僚機構による実行**というパイプラインを通してのみ都市に干渉できる。情報は新聞・地図・側近報告の三層で与えられ、いずれも完全には信頼できない。プレイヤーは限られた情報を反芻し、文字数制限下で「その時点で正しい勅令」を出す難しさに挑む。

### 1.2 検証すべき中核仮説

> 信頼性が曖昧な情報を反芻した上で、その時点で正しい勅令を出し、意図通りに発展させる難しさが面白いか。

プロトタイプはこの仮説の検証に特化し、その他の機能（イベント、複数新聞、教育、派閥工作など）は製品版で実装する。

## 2. 世界観と成長軸

架空の辺境の地に領主として着任したプレイヤーが、村から国家まで発展させる。1ターン＝1年。

| ステージ | 人口目安 | 側近 | 官僚機構 | 解釈ズレの性質 |
|----------|----------|------|----------|----------------|
| 村 | 〜500 | 1〜2人 | なし | 側近の能力・野心のみ |
| 町 | 〜5,000 | 2〜3人 | 3〜5人 | 派閥・汚職が発生 |
| 都市 | 〜5万 | 3〜5人 | 10人以上、部署制 | 部署間の縄張り争い |
| 国家 | 〜100万 | 5人以上 | 省庁制 | 意図が数段階歪む |

**設計思想**：ステージが上がるほど「プレイヤーの意図が届きにくくなる」。難易度曲線であり、同時に「国家規模では直接統治は不可能で、機構設計そのものがゲームになる」というテーマの表現。

## 3. コアループ

```
① プレイヤーが「意図」を宣言（任意）＋勅令（自然言語、文字数制限あり）を発行
        ↓
② 参謀（Mistral API）が勅令を解釈し、都市パラメータへの操作指示をJSONに変換
        ↓
③ 側近がその指示を「歪めて」実行（忠誠心・能力・野心・派閥）
        ↓
④ 官僚機構がさらに歪めて実行（町以降）
        ↓
⑤ 都市が変化（ルールエンジンで決定論的に更新）
        ↓
⑥ 新聞・地図・側近報告として結果が返る
        ↓
⑦ プレイヤーが情報を突合・分析し、任命/解任または新たな勅令で修正
        ↓
（①へ戻る）
```

1ターン＝1年＝勅令1回＋手動介入（任命/解任）。ターン制でテンポを管理する。

## 4. 情報UIの三層構造

プレイヤーは都市を直接見られない。3つの媒体を通してのみ現状を知る。

### 4.1 新聞（静的情報）

- ターン終了時に発行。世論・事件・統計を掲載。
- 偏向がある：新聞社の思想、検閲、官僚の圧力で内容が歪む。
- プレイヤーは「新聞を信じるか、側近に確認するか」を迫られる。
- **プロト**：1紙のみ、テキスト形式。テンプレート＋スロットで生成（LLM不使用）。偏向度は固定（30）。
- **製品版**：複数紙、論調対立を政治要素に。

### 4.2 地図（視覚的情報）

- 区画・建物・道路がグリッド上に表示され、発展が目に見える。
- 「見た目」と「実態」が一致しないことがある。
- データ構造として `visual_state` と `actual_state` を別に保持。
- **プロト**：10×10の抽象グリッド、色分けのみ。区画は自動配置。`actual_state` は側近報告経由でのみテキスト開示。
- **製品版**：ローポリのジオラマ表現、プレイヤーによる区画指定、霧。

### 4.3 側近（動的情報）

- プレイヤーに直接報告する数人の側近。勅令は彼らに渡す。
- 側近自身のパラメータで報告が歪む。能力が低いと見落とし、野心が高いと都合の悪い情報を隠す、派閥を持つと他派閥の功績を貶す。
- 「動的に現状を知る手段」だが、その情報自体が信頼できないという二重性が核。
- **プロト**：2人固定、テキスト報告。
- **製品版**：側近同士の対立・讒言・出世競争をナラティブイベントとして実装。

## 5. 側近・官僚システム

### 5.1 二層構造

```
プレイヤー
   ↓ 勅令
側近（参謀）── 勅令を解釈し、官僚への指示に翻訳
   ↓ 指示
官僚機構 ── 派閥・汚職・能力で指示を歪めて実行（町以降）
   ↓
都市（ルールエンジンで決定論的に更新）
```

### 5.2 側近パラメータ

| パラメータ | 範囲 | 効果 |
|------------|------|------|
| 忠誠心 | 0–100 | 低いと報告を歪める、最悪寝返る |
| 能力 | 0–100 | 低いと解釈ミス・報告の見落とし |
| 野心 | 0–100 | 高いと功を焦り、無理な実行や隠蔽 |
| 派閥 | 開発/商業/保守/軍事/環境 | 報告・解釈に思想的偏り |
| 専門性 | インフラ/経済/治安/環境 | 専門外の分野で精度低下 |
| 信頼関係 | 0–100 | プレイヤーとの関係値。低いと報告が減る |

### 5.3 官僚パラメータ（製品版・町以降）

| パラメータ | 範囲 | 効果 |
|------------|------|------|
| 忠誠心 | 0–100 | 低いと勅令を無視・歪曲 |
| 能力 | 0–100 | 低いと実行ミス |
| 汚職 | 0–100 | 高いと予算横領・計画の私物化 |
| 派閥 | 同上 | 派閥思想で解釈が偏る |
| 専門性 | 同上 | 専門外の勅令は精度低下 |
| 手続きの複雑さ | 1–5層 | 正確性↑だが速度↓・コスト↑ |

### 5.4 手動介入

**プロト**：任命/解任のみ。

- 任命コスト：政治資本1。候補2人から選択。
- 解任コスト：0（更迭は君主の権限）。
- 側近全員解任：許容するが、側近なしでは勅令が実行されず実質詰み。ゲームオーバー条件には含めない。

**製品版**：教育、監査、派閥工作、機構改編を追加。

## 6. 勅令システム（意図宣言＋ボーナス）

### 6.1 入力仕様

- 1ターンに発行できる勅令は1つ。
- 文字数制限あり（暫定40文字、タグ1つにつき5文字消費。プロトで調整）。
- タグは任意で付与：対象 / 規模 / 期限 / 優先度。
- 文字数超過時は送信不可。UIに残り文字数を常時表示。

### 6.2 意図宣言システム

勅令発行の前に、プレイヤーは「意図」を任意で宣言できる。

- **意図**：この勅令で達成したい具体的な目的（例：「人口を+20増やす」）。
- 意図は任意入力。空欄でも勅令は発行可能。
- 意図を宣言した場合、ターン終了時に「宣言した意図 vs 実際の結果」の比較行が3段表示に追加される。
- **ボーナス**：意図が達成された場合、政治資本+1 または 幸福度+5（プロトで調整）を付与。
- **機械採点は行わない。** 意図達成の判定は、宣言した意図と実際のパラメータ変化の単純比較のみ。隠された「最適解」は存在しない。

> 設計意図：意図宣言は「プレイヤー自身が何を達成したかったか」を明確にし、事後自己評価を助ける。ボーナスは「意図通りに動かす」動機づけになるが、ペナルティは設けない。

### 6.3 解釈パイプライン

```
勅令テキスト
  → [意図抽出] Mistral APIが対象・規模・期限・優先度をJSON化（Structured Outputs）
  → [側近解釈] 精度 = f(能力, 専門一致, 信頼)
  → [側近の歪み] 強度 = f(野心, 派閥対立, 忠誠心)
  → [官僚補正] ※町以降
  → [実行] ルールエンジンがパラメータ更新
  → [意図判定] 宣言された意図との比較（任意）
```

### 6.4 歪みの種類

| 歪み | 発生条件 | 効果 |
|------|----------|------|
| 規模の誤読 | 能力低 | 指示量が±30〜50%変動 |
| 対象の取り違え | 専門外 | 別パラメータに作用 |
| 骨抜き | 派閥対立 | 効果量が半減 |
| 隠蔽 | 野心高＋忠誠低 | 報告から悪化情報が消える |
| 横領 | 汚職高（町以降） | 国庫が余分に減る |

### 6.5 結果の可視化（3段表示＋意図比較）

ターン終了時に以下を並べて表示する。

1. **参謀の解釈**：Mistral APIの出力JSONを平易に表示
2. **側近による補正**：どこがどう歪んだか
3. **実際の結果**：パラメータの変化
4. **意図比較**（宣言した場合のみ）：「宣言した意図」vs「実際の結果」、達成/未達、ボーナス有無

### 6.6 プロンプトインジェクション対策

- 勅令はあくまで「ゲーム内の命令」として扱い、システムプロンプトを上書きするメタ命令（「官僚を無視せよ」等）はルールエンジン側でサニタイズ。
- Mistral APIの責務は翻訳層に限定。
- Structured Outputs の JSON Schema をプロキシ側から固定し、フロントから改ざんできないようにする。

## 7. ゲームパラメータとバランス

### 7.1 都市パラメータ（プロト：5種＋政治資本）

| パラメータ | 初期値 | 範囲 | 備考 |
|------------|--------|------|------|
| 人口 | 120 | 0–∞ | ターン終了時に増減 |
| 国庫 | 500 | 0–∞ | 建築・給与で減少、税収で増加 |
| 幸福度 | 50 | 0–100 | 50未満で人口流出 |
| インフラ | 10 | 0–100 | 住宅・道路・井戸など |
| 汚職率 | 5 | 0–100 | 村では低い |
| 政治資本 | 3/ターン | 0–10 | 勅令発行（1）・任命（1）のコスト |

### 7.2 マルチエンディング方式

| エンディング | 条件 | 表示 |
|--------------|------|------|
| ゲームオーバー：人口壊滅 | 人口が0になる | 「領地は無人となった」 |
| ゲームオーバー：財政破綻 | 国庫がマイナスになる | 「国庫は底を突いた」 |
| ゲームオーバー：民衆離反 | 幸福度が0になる | 「民衆は領主を見限った」 |
| 成功：村→町遷移 | 人口300＋インフラ25＋役所建設 | 遷移演出→即終了 |
| 失敗：目標未達 | 50ターン終了時に目標未達 | 「村は町になれなかった」 |

ゲームオーバーは即座に終了し、リスタートできる。高難度だが、失敗から学べるテンポを確保する。

### 7.3 プロトの目標（村→町）

**人口300以上 ＋ インフラ25以上 ＋ 役所の建設。** 達成した瞬間に遷移演出が入り、即終了。

### 7.4 難度設計

高め。30〜50ターンで目標到達するには以下が必要：

- 資源のやりくり（税収と支出のバランス）
- 情報の突合（新聞・側近報告・地図の乖離を見抜く）
- 側近の掌握（能力と忠誠のトレードオフ）
- 勅令の精度（文字数制限下での表現選択）
- 意図の明確化（ボーナス獲得のための目的設定）

**難度調整レバー**：税収レート、人口増加率、側近の歪み確率、勅令1回の国庫コスト。プロトでテスターの到達率を見て調整。

### 7.5 側近の初期パラメータ（プロト）

| パラメータ | 側近A（老練な代官） | 側近B（若い商人上がり） |
|------------|---------------------|--------------------------|
| 忠誠心 | 80 | 60 |
| 能力 | 60 | 75 |
| 野心 | 30 | 70 |
| 派閥 | 開発 | 商業 |
| 専門性 | インフラ | 経済 |
| 信頼関係 | 70 | 50 |

### 7.6 側近解釈精度（暫定式）

```
accuracy = clamp(
    0.3
  + ability / 200
  + (専門一致 ? 0.2 : 0)
  + (信頼 > 70 ? 0.1 : 0)
  - (野心 > 70 && 派閥対立 ? 0.2 : 0),
  0, 1)
```

## 8. 地図・区画メカニクス（自動配置）

### 8.1 基本方針

プロトでは、プレイヤーが区画を直接指定する操作は実装しない。勅令は数値パラメータを動かし、地図はその結果を自動的に反映する。

### 8.2 区画の自動導出

| 区画種別 | 導出式（例） | 備考 |
|----------|--------------|------|
| 住宅区画 | `floor(人口 / 20)` | 人口増加に応じて自動増加 |
| 道路区画 | `floor(インフラ / 5)` | インフラ整備に応じて自動増加 |
| 役所 | 勅令「役所を建てよ」でフラグON | 1区画固定 |
| 空き地 | 残余 | 常に一定数確保 |

- 区画はグリッド上に自動配置（優先順位：役所 → 道路 → 住宅 → 空き地）。
- プレイヤーは区画の位置を指定できない。「意図通りにいかない」体験の一部として、自動配置の結果を見て「なぜこうなったか」を側近報告と突合する。

### 8.3 見た目と実態の乖離

- `visual_state`：区画の見た目。
- `actual_state`：実際の状態（稼働中/空洞/塩漬け）。
- 乖離は側近報告経由でのみテキスト開示される（例：「立派な倉庫に見えるが、中は空です」）。
- プロトでは視覚的な乖離表示は実装しない（ただし §12.7 の亀裂アイコンは、報告で開示された場合のみ表示）。

## 9. プロトタイプ仕様

### 9.1 スコープ

| 項目 | プロト | 製品版 |
|------|--------|--------|
| ステージ | 村→町のみ（遷移即終了） | 村→国家 |
| ターン数 | 30〜50（1ターン＝1年） | 数百ターン |
| 手動介入 | 任命/解任のみ | 教育・監査・派閥工作・機構改編 |
| 新聞 | 1紙・テキスト | 複数紙・論調対立 |
| 地図 | 10×10抽象グリッド、自動配置 | ジオラマ、区画指定、霧 |
| イベント | なし（システムの創発のみ） | ナラティブイベント多数 |
| LLM | Mistral API＋プロキシ | Mistral API／ローカル選択可 |
| 配布 | ブラウザのみ | Steam（Tauri） |
| 言語 | 日本語のみ | 英語・ドイツ語（体験版から）、中国語検討 |
| UIデザイン | 紙の質感（簡易）、判子アニメ、3層書類表示 | 高解像度テクスチャ、手書きフォント、紙めくり3D、地図の霧 |
| 技術 | Effect-TS + Phaser + Vite | 同左 + Tauri |

### 9.2 プロトの合格ライン

- テスターが自発的にもう1回遊ぶ
- 「報告がズレてた」と口に出す
- 勅令の書き方を工夫し始める（文字数制限を意識した表現の変化）
- 意図宣言を使い始める（ボーナスを狙う動機）
- 目標到達率がテスターの **30〜50%**
- ゲームオーバー率が **20〜40%**

### 9.3 プロトで検証する項目

1. 中核仮説（情報の反芻と勅令の難しさが面白いか）
2. 文字数制限の適切さ（40文字が厳しすぎ/緩すぎでないか）
3. 側近の歪みの許容範囲（理不尽と面白さの境界）
4. 3段表示＋意図比較の有効性
5. 難度の妥当性（到達率30〜50%、ゲームオーバー率20〜40%）
6. ゲームオーバーの頻度と納得感
7. UIの雰囲気が「判断の重み」を伝えているか（判子を押す感覚、書類を読む緊張感）

## 10. 言語・i18n方針

| 段階 | 対応言語 | 備考 |
|------|----------|------|
| プロトタイプ | 日本語のみ | コミュニティ内テスト用 |
| 体験版 | 英語・ドイツ語 | 海外展開を見据え、体験版から対応 |
| 製品版 | 英語・ドイツ語＋中国語 | 中国語は有識者確保が条件、翻訳リソース次第 |

- プロト段階から文言は `messages.ts` に集約し、i18n化できる構造にしておく。
- Mistral APIは日本語・英語・ドイツ語・中国語を含む多言語に対応。
- フォントは言語ごとに切り替え（i18nとフォントはセットで管理）。

### 11.1 スタック

| 層 | 技術 | 責務 |
|----|------|------|
| UI/描画 | Phaser | 地図描画、入力 |
| UI/パネル | DOM（React/Svelte等） | 新聞・側近パネル・勅令入力・意図宣言 |
| ゲームロジック | Effect-TS | 状態機械、解釈パイプライン、副作用管理 |
| 配布（プロト） | Vite + 静的ホスティング | ブラウザのみ |
| 配布（製品） | Tauri | Steamラップ、Steamworks連携 |
| LLM | Mistral API | 勅令→意図JSONの翻訳層 |
| LLMプロキシ | Cloudflare Workers（Renderも可） | APIキー隠蔽、レート制限、ログ収集 |

### 11.2 Mistral API 仕様

| 項目 | 仕様 |
|------|------|
| モデル | `mistral-small-latest`（単価：旧記載「入力0.60 per M tokens」。通貨・出力単価が不明のため要確認） |
| 出力形式 | **Structured Outputs（JSON Schema）を第一選択**。`response_format.type = json_schema` で厳格にスキーマを強制 |
| フォールバック① | JSONモード（`response_format.type = json_object`） |
| temperature | 0〜0.3 |
| タイムアウト | 5秒 |
| リトライ | 2回（指数バックオフ） |
| フォールバック② | テンプレートパーサー（ゲームを止めない） |
| 多言語 | 日本語・英語・ドイツ語・中国語対応 |

**Structured Outputs のスキーマ：**

```json
{
  "name": "decree_intent",
  "strict": true,
  "schema": {
    "type": "object",
    "properties": {
      "action": { "type": "string", "enum": ["build", "tax", "invest", "reform", "appoint", "dismiss"] },
      "target": { "type": "string" },
      "magnitude": { "type": "number", "minimum": -100, "maximum": 100 },
      "budget": { "type": "number" },
      "confidence": { "type": "number", "minimum": 0, "maximum": 1 }
    },
    "required": ["action", "target", "magnitude", "budget", "confidence"],
    "additionalProperties": false
  }
}
```

### 11.4 主要な型（Effect-Schemaスタイル）

```ts
// GameState（不変）
type GameState = {
  turn: number;
  stage: "village" | "town";
  params: {
    population: number;
    treasury: number;
    happiness: number;
    infrastructure: number;
    corruption: number;
  };
  aides: Aide[];
  politicalCapital: number;
  officeBuilt: boolean;
  history: TurnRecord[];
  ending: Option<Ending>;
};

// Decree
type Decree = {
  text: string;
  tags: DecreeTag[];
  // バリデーション: text.length + tags.length * 5 <= 40
};

// IntentDeclaration
type IntentDeclaration = {
  declared: boolean;
  targetParam: "population" | "treasury" | "happiness" | "infrastructure" | "corruption";
  targetValue: number;
  direction: "increase" | "decrease" | "absolute";
};

// DecreeIntent（Mistral出力）
type DecreeIntent = {
  action: "build" | "tax" | "invest" | "reform" | "appoint" | "dismiss";
  target: string;
  magnitude: number;
  budget: number;
  confidence: number;
};

// TurnRecord
type TurnRecord = {
  turn: number;
  decree: Decree;
  intentDeclaration: Option<IntentDeclaration>;
  intent: DecreeIntent;
  aideAdjustment: AideAdjustment;
  actualResult: ParamDelta;
  intentAchieved: Option<boolean>;
  bonusApplied: Option<Bonus>;
  newspaper: NewspaperArticle;
};

// Ending
type Ending =
  | { kind: "gameover"; reason: "population" | "treasury" | "happiness" }
  | { kind: "success"; stage: "town" }
  | { kind: "timeout" };
```

### 11.5 ターン状態機械（Effect）

```ts
const playTurn = (state: GameState, decree: Decree, intentDecl: Option<IntentDeclaration>) =>
  Effect.gen(function* (_) {
    yield* _(checkEnding(state));
    yield* _(validateDecree(decree));
    const intent = yield* _(LLMService.parseDecree(decree, state));
    const aide = selectAide(state, intent);
    const adjusted = aideInterpret(aide, intent);
    const nextParams = applyIntent(state.params, adjusted);
    const { achieved, bonus } = evaluateIntent(intentDecl, state.params, nextParams);
    const finalParams = applyBonus(nextParams, bonus);
    const mapState = updateMap(finalParams, state.officeBuilt);
    const newspaper = generateNewspaper(finalParams, state, adjusted);
    const record: TurnRecord = { /* ... */ };
    const nextState = {
      ...state,
      turn: state.turn + 1,
      params: finalParams,
      history: [...state.history, record],
      ending: determineEnding(finalParams /* , ... */),
    };
    yield* _(SaveService.save(nextState));
    return nextState;
  });
```

**エラー型**：`ValidationError | LLMError | SaveError | GameOverError`

### 11.6 Mistral APIプロキシ

```
[ブラウザ] → [Vite dev / 静的ホスティング]
                ↓ fetch（簡易トークン付き）
         [Cloudflare Workers / Render]
                ↓ Mistral APIキー付き
         [Mistral API（mistral-small-latest）]
```

- プロキシでAPIキーを隠蔽、レート制限、呼び出しログ収集。
- Structured Outputs の JSON Schema をプロキシ側で固定し、フロントから改ざん不可。
- プロトでは簡易トークンのみ（身内テスト）。

### 11.7 セーブデータ

都市状態、側近状態、新聞履歴、ターン記録をJSONで保持（localStorage）。LLM会話履歴は保存しない。

## 12. UIデザイン方針（Paper, Please × Civilization）

### 12.1 コンセプト

**「机の上の書類と、広げた地図」** — プレイヤーは領主の執務机に座り、新聞・報告書・地図を広げ、判子を押し、勅令をしたためる。

Paper, Please の書類・審査・判断の重みと、Civilization のマップ中心の成長可視化を、羊皮紙とインクの質感で統一する。

### 12.2 画面レイアウト（3層の物理的メタファー）

```
┌─────────────────────────────────────────────┐
│  [上部：執務机の天板（木目）]                  │
│                                             │
│  ┌──────────┐  ┌──────────────────────┐    │
│  │ 新聞      │  │  地図（Civ風タイル）   │    │
│  │（紙面）   │  │  10×10グリッド        │    │
│  └──────────┘  └──────────────────────┘    │
│                                             │
│  ┌──────────┐  ┌──────────────────────┐    │
│  │ 側近報告  │  │  勅令入力（巻物/書簡）  │    │
│  │（書簡）   │  │  意図宣言欄            │    │
│  └──────────┘  └──────────────────────┘    │
│                                             │
│  [判子を押す＝ターン実行]                     │
└─────────────────────────────────────────────┘
```

- **新聞**：折り畳まれた新聞を広げる。見出しは活字風。
- **地図**：机の上に広げた羊皮紙。タイルはCiv風だが彩度低め。
- **側近報告**：封蝋を割って開く書簡。側近ごとに筆跡が異なる（プロトではフォント統一、製品版で差）。
- **勅令入力**：巻物または書簡。送信＝判子を押す。
- **意図宣言**：勅令の余白に「目的」を書き添える欄。

### 12.5 インタラクション（触覚的フィードバック）

- **判子を押す**：ターン実行時、朱色の判子が「ドン」と押されるアニメーション＋効果音。決定の重みを表現。

### 12.6 3段表示（解釈／補正／結果）の見せ方

Paper, Please の「書類の重なり」メタファーで表現する。

```
┌─────────────────────────────────┐
│  【参謀の解釈】                  │  ← 一番上の書類
│  「住宅を15区画建てる」           │
│  ─────────────────────          │
│  【側近による補正】              │  ← めくると下から出る
│  「10区画に減らされた（骨抜き）」  │
│  ─────────────────────          │
│  【実際の結果】                  │  ← 一番下
│  人口 +8、国庫 -300              │
│  ─────────────────────          │
│  【意図比較】※宣言時のみ          │
│  意図：人口+20 → 結果：+8（未達） │
└─────────────────────────────────┘
```

- 書類が3枚重なっており、めくることで下の層が見える。
- 差分は朱色の訂正線で示す。
- 意図比較は余白に鉛筆で書いたメモ風。

### 12.7 地図（Civilization風）のスタイル

- タイルベース：10×10グリッド。Civのタイル感を出すが、彩度低めの羊皮紙風。
- タイル種別：空き地（羊皮紙の地）、住宅（小さな家アイコン）、道路（線）、役所（旗）、市場。
- 成長の可視化：人口増加で住宅タイルが自動出現。
- 見た目と実態の乖離：`actual_state` が空洞の建物は、側近報告で開示された場合のみタイルに小さな亀裂アイコンを表示。

### 12.8 プロトと製品版の差分

| 要素 | プロト | 製品版 |
|------|--------|--------|
| 紙の質感 | CSSテクスチャ1枚 | 高解像度テクスチャ、経年変化 |
| 判子アニメーション | 簡易（1秒） | 効果音付き、紙の凹み表現 |
| 紙めくり | フェードのみ | 3Dめくり |
| 手書き風フォント | 使わない（Noto Serif JPで統一） | 側近ごとに手書き風フォント |
| 地図の霧 | なし | あり |
| タイルの成長演出 | 即時表示 | ふわっと出現 |

### 12.9 実装上の注意（Phaser + DOM）

- DOMパネル（新聞・書簡・勅令入力）はCSSで紙の質感を表現。`background-image` にテクスチャ、`box-shadow` で紙の重なり。
- Phaser地図はタイルスプライト。彩度を落としたテクスチャ。
- 判子アニメーションはDOM（CSS transition）で実装。
- フォントは `@font-face` で Noto Serif JP / Noto Sans JP を読み込み（OFL、商用可）。

## 14. リスクと対策

| リスク | 対策 |
|--------|------|
| Mistral APIコスト超過 | ターン制、翻訳層限定、キャッシュ、小型モデル |

| 意図宣言が無視される | ボーナス設計で動機づけ。任意入力なので強制しない |
| AI規制（EU AI Act等） | 生成コンテンツ表示、年齢レーティング対応 |
